## 3. Apply the migrations (owner)

PLAN §12 says production migrations are owner-run.

1. From a clean checkout of the **reviewed** `main` commit, run `supabase link --project-ref <ref>` (Supabase CLI 2.122.1, already pinned in `package.json`).
2. Run `supabase db push`. Check that it lists exactly the files in `supabase/migrations/` and nothing else.
3. **Don't** run `supabase/seed.sql` against production. It holds synthetic test data only.
4. Record the migration count and the latest migration file name in the receipt (section 10).

## 4. Database roles and Auth settings (owner)

**4.1 The `catalogue_server` login (D-081).** The migrations create it as `LOGIN NOINHERIT NOBYPASSRLS` with a connection limit of 10 and **no password**. In the SQL editor, set one:

```sql
alter role catalogue_server password '<generated, 32+ random characters>' valid until '<date about 12 months ahead>';
```

Store the password in your password manager only. You'll paste it once, into Hyperdrive (step 6). Supabase's daily backups don't keep custom-role passwords ([Backups](https://supabase.com/docs/guides/platform/backups), read 2026-11-10), so after any restore you set it again.

**4.2 Exposed schemas.** In the project's API settings, the exposed schemas must be `public` and `graphql_public` only, the same as `supabase/config.toml`. `api` and `private` must **not** be exposed (D-081).

## 6. Hyperdrive for `CATALOGUE_DB` and `FORMS_DB` (owner)

Two configurations, one per scoped login: `catalogue_server` (search and listings, D-081) and `forms_server` (visitor forms, Claude 22). Set a `forms_server` password the same way as step 4.1 (`connection limit 5` is already in the migration). Do steps 1 to 3 below for each.

1. Cloudflare dashboard → **Hyperdrive → Create configuration**, or `wrangler hyperdrive create carworx-catalogue-production --connection-string="postgres://catalogue_server:<password>@<host>:<port>/postgres" --caching-disabled`.
2. **Caching must be off.** Hyperdrive caches by default, for 60 seconds, and "does not purge or invalidate cached read query results when your application writes" ([Query caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/), read 2026-11-10). Caching would keep a suspended listing visible. The `--caching-disabled` flag is documented in [Wrangler Hyperdrive commands](https://developers.cloudflare.com/workers/wrangler/commands/hyperdrive/), read 2026-11-10.
3. **Which host: an open question (OQ-1).** Cloudflare's Supabase page says to use the **Direct connection** string, not the pooled one ([Hyperdrive + Supabase](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/), read 2026-11-10). Supabase says the free plan's direct connection is **IPv6 only**, and the shared pooler is IPv4 ([Connecting to Postgres](https://supabase.com/docs/guides/database/connecting-to-postgres), read 2026-11-10). Claude 19 §9 assumed the pooler. **Try the direct connection on staging first.** If Hyperdrive can't reach it, use the shared pooler in **session mode** and record why. Don't buy the IPv4 add-on (it's paid).
4. Copy each Hyperdrive **ID** (not secret) into the config PR (step 5). It replaces `OWNER_SETS_PRODUCTION_CATALOGUE_DB_HYPERDRIVE_ID` and `OWNER_SETS_PRODUCTION_FORMS_DB_HYPERDRIVE_ID` in `apps/web/wrangler.jsonc`. Staging has its own two placeholders; never reuse a staging ID.

## 7. Worker secrets and variables (owner)

Set with `wrangler secret put <NAME> --env production` or in the dashboard ([Secrets](https://developers.cloudflare.com/workers/configuration/secrets/), read 2026-11-10). **Values never go into Git, chat, a PR or a receipt.**

### 7.1 App Worker `carworx-web-production`

| Name | Kind | What it is | Source of the name |
|---|---|---|---|
| `APP_ORIGIN` | var | `https://carworx.app` | `.env.example`, T3 |
| `SUPABASE_URL` | var | The production API URL | `.env.example`, T3 |
| `CARWORX_ENV` | var | `production` (see gap P-3) | `wrangler.jsonc`, K2 |
| `SUPABASE_PUBLISHABLE_KEY` | secret | The production publishable (anon) key. **Never** the service-role key | `.env.example`, K2 README |
| `SEARCH_CURSOR_KEY` | secret | 32+ random characters, signs search cursors and map pins | `.env.example`, D-081, D-084 |
| `SEARCH_LIMITER_SALT` | secret | 32+ random characters, keys the limiter | `.env.example`, D-081 |
| `MAPBOX_SERVER_TOKEN` | secret | Server-only Mapbox token: geocoding plus `styles:tiles` | `.env.example`, D-084 |
| `SEARCH_LIMITER` | Durable Object binding | Class `SearchLimiter`, SQLite | `wrangler.jsonc`, D-081 |
| `CATALOGUE_DB` | Hyperdrive binding | Caching **off**, as `catalogue_server` | `wrangler.jsonc`, `.env.example`, D-081 |
| `FORMS_DB` | Hyperdrive binding | Caching **off**, as `forms_server` | `wrangler.jsonc`, `.env.example`, Claude 22 |
| `TURNSTILE_SITE_KEY` | var (public) | **Proposed name**, fixed by Bundle B (gap P-5) | Claude 17 §3 |
| `TURNSTILE_SECRET_KEY` | secret | **Proposed name**, fixed by Bundle B (gap P-5) | Claude 17 §3 |

Use **different** random values from staging for every secret. Rotating `SEARCH_CURSOR_KEY` only invalidates open cursors and map links, which is safe.

### 7.2 Names that must **not** be set in production

| Name | Why |
|---|---|

| `STAGING_APPROVED_RECIPIENTS_JSON`, `STAGING_PROBE_EVENT_KEY`, `STAGING_PROBE_ORIGIN`, `STAGING_PROBE_ADMIN_KEY` | Staging test controls |

### 7.3 Owner-held, never on a Worker

The Supabase database password, the `catalogue_server` password (it lives inside Hyperdrive only), your Cloudflare and Supabase logins, the backup encryption private key (D-072) and the Google OAuth client secret (it lives in Supabase Auth settings).

## 8. Deploy (owner)

Run by the owner from their own machine with their own Cloudflare login. An agent environment never holds a production token (PLAN §12).

1. Check out the exact `main` commit that the coordinator and the owner approved. Run `pnpm run check`.
2. Build with `CLOUDFLARE_ENV=production` set **during the build**. Choosing the environment only at deploy time doesn't fix a default build (K2 README, "Manual workflow and source evidence").
3. Run `wrangler deploy` from `apps/web` (pinned Wrangler). The Durable Object migration applies on the first deploy.
4. Record the Worker version ID and the commit SHA.

## 9. Smoke checks (owner, after deploy)

| Check | Pass when |
|---|---|
| `GET /healthz` | 200, fixed JSON, `Cache-Control` contains `no-store` |
| `GET /` and a category page | 200, no dev-page links, no `noindex` |
| A search for a synthetic point | 200 or an honest empty state; never a 503 |
| `/search/map` without a signed link | Refused |
| Response headers on `/account` | `private, no-store` |
| A dev page path | 404 |

Send only these (no secret values): the project ref and region, the migration count and the latest file name, the Worker name and version ID, the commit SHA, the Hyperdrive config **ID** and "caching disabled: yes", the list of secret **names** set (from `wrangler secret list`), the smoke results, and the date and time in SAST.
